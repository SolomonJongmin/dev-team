# 보안 셀프 체크리스트

인증·승인·비밀값·메시지 수신·설정 저장·프로세스 수명을 건드린 개발자는 제출 전에 이 목록을 확인한다.

## 쓰는 법
1. 변경 경로와 연결된 영역을 읽고 각 질문에 예/아니오/해당 없음으로 답한다. 예에는 코드 위치·검증 결과를 붙인다.
2. 아니오·미검증은 실패 시나리오와 보완 계획을 적어 리뷰어에게 넘긴다. 해당 없음은 근거를 적는다.
3. 결과 표를 보고에 붙인다.

각 항목의 "사례"는 실제 리뷰에서 잡힌 결함 유형이다.

## 비밀값 경로
- [ ] 비밀값이 입력부터 암호화 저장까지 모델 출력·세션 기록·감사 로그·외부 알림으로 새지 않는가?
- [ ] 자격 증명이 담긴 URL·헤더가 일반 권한으로 읽을 수 있는 큐·테이블에 평문으로 들어가지 않는가? — 사례: 웹훅 URL이 DB 요청 큐에 평문 저장.
- [ ] UI fallback·구버전 호환 경로도 URL의 사용자정보·쿼리·fragment를 제거하는가? — 사례: 결과 카드가 토큰 포함 URL을 그대로 표시.
- [ ] 본문뿐 아니라 제목·집계·요약에도 개인정보·비밀값 필터가 적용되는가? — 사례: 사용량 집계의 세션 제목에 전화번호.
- [ ] 비밀번호는 실제 password 입력란에만 기록되는가? — 사례: `textarea type=password`가 속성 검사만 통과해 평문 표시.
- [ ] 페어링 코드·토큰이 모델 결과·시작 로그에서 빠지는가?

## 메시지 발신자 검증
- [ ] 채널·포트 이름이 아니라 플랫폼이 보증하는 발신자 ID·출처를 검증하는가? — 사례: content script가 내부 패널 포트 이름을 써서 승인 이벤트를 받음.
- [ ] Origin 허용 목록과 별개로 비밀 토큰 또는 신뢰된 연결 인증을 요구하는가? — 사례: 로컬 프로세스가 Origin 헤더를 위조해 토큰 없이 비밀 조회.
- [ ] 승인 응답은 요청 ID 외에 실제 소유 연결·세션까지 대조하는가? — 사례: 다른 연결이 요청 ID를 얻어 응답을 위조.
- [ ] 요청을 제한한 정책이 응답·broadcast에도 똑같이 적용되는가?
- [ ] 생략 가능한 입력 필드가 아니라 인증된 연결에서 출처를 정하는가? — 사례: 출처 필드 생략이 기본값(신뢰)으로 처리.
- [ ] 같은 계정이라도 미승인 기기는 수신 권한이 거부되는가?

## 출처·origin 고정
- [ ] 모든 비밀 조회·자동 입력 진입점에서 HTTPS와 명시적 예외만 허용하는가?
- [ ] 출처를 최상위 탭·요청 payload가 아니라 실제 요청 프레임에서 얻는가? — 사례: 교차 출처 iframe이 상위 사이트 자격 증명을 받음.
- [ ] URL과 실제 origin 불일치, null·opaque origin을 거부하는가?
- [ ] 상·하위 도메인·www·포트 공유는 명시적 정책에만 따르고 정확한 호스트를 우선하는가?
- [ ] 승인 당시의 탭·전체 origin이 실제 제출 단계까지 전달되는가? — 사례: hostname만 대조해 다른 포트로 비밀번호 전송.
- [ ] 존재 판정·조회·갱신이 같은 출처 매칭 정책을 쓰는가?

## 승인 게이트
- [ ] 재사용 승인이 모델이 주장하는 action이 아니라 검증 가능한 실제 실행에 묶이는가? — 사례: 삭제·구매를 "submit"으로 요청해 이전 승인 재사용.
- [ ] 승인 기억은 사용자가 명시적으로 고른 경우에만 저장되는가?
- [ ] 새 승인 경로뿐 아니라 영구 허용·직접 핸들러·외부 도구의 우회 경로도 검사했는가?
- [ ] 승인 범위가 실행·탭·origin·항목에 묶이는가?
- [ ] "저장 안 함" 선택이 자동 캡처 등 모든 저장 경로에서 지켜지는가?
- [ ] 감사 기록만으로 실제 출처·실행·원승인·재사용을 추적할 수 있는가?

## 확인과 사용 사이 경쟁 (TOCTOU)
- [ ] 승인 대기 뒤 실제 입력 직전에 고정한 탭·origin을 다시 검사하는가?
- [ ] 비밀값 기록이 검증한 문서·요소에 직접 묶이고, 페이지 이벤트가 대상을 바꾸지 못하는가?
- [ ] 동기 호출 안에서도 focus·편집 이벤트 재진입 가능성을 검토했는가?
- [ ] 중지·만료 뒤 모든 await 경계에서 입력·제출·저장을 차단하는가?
- [ ] 늦게 도착한 응답은 사용자가 바꾼 최신 버전과 일치할 때만 반영되는가?
- [ ] 만료와 복원·저장·재로드가 겹쳐도 이전 세대 상태가 되살아나지 않는가?

## 재연결·재시작
- [ ] 연결이 끊기면 대기 중 요청을 안전하게 끝내거나 인증된 새 연결에 다시 묶는가?
- [ ] 재접속을 "새 인스턴스 성공"으로 착각하지 않는가? — 사례: 같은 프로세스 재접속을 재시작 성공으로 오인.
- [ ] 절대 deadline과 진행 상태가 worker 재시작 뒤에도 복원되는가?
- [ ] 타임아웃 난 자식 프로세스는 취소되고, 늦은 완료가 정상 자식을 죽이지 않는가?
- [ ] spawn·포트 점유를 준비 완료로 간주하지 않고, 준비·소유권·인계 확인 뒤 단독 작업을 시작하는가?
- [ ] 연결 복구 스트림에 중복 조각과 이전 세대 조각을 구분할 식별자가 있는가?

## 판정 휴리스틱
- [ ] 성공(로그인 등)은 오류·로딩·빈 화면을 빼고 명시적 근거가 있을 때만 확정하는가?
- [ ] 사람에게 넘겼다 돌아온 경로에도 같은 성공 근거·출처 검증을 적용하고, 미확인은 unknown으로 남기는가?
- [ ] 읽기 도구 실행 성공과 사용자 작업 완료를 구분하는가?
- [ ] 페이지 본문 정규식이 아니라 도구가 낸 구조적 실패 상태를 쓰는가? — 사례: 페이지의 "WARNING" 문자열이 정상 작업을 실패로 바꿈.
- [ ] 실패가 구조화된 채로 생산자부터 소비자(batch 등)까지 전달되는가?
- [ ] 날짜·수치 입력의 형식·시간대·유한성·경계값을 명시적으로 검증하는가? — 사례: DB가 허용하는 `infinity`가 만료 없는 유료 등급이 됨.

## 한도·동시성
- [ ] 비용 한도는 진행·예약 건수를 포함해 실제 호출 직전에 원자적으로 확보하는가? — 사례: 하루 상한 1에서 두 세션이 동시에 통과.
- [ ] 실제 호출을 건너뛰면 예약 슬롯을 소비하지 않는가?
- [ ] 키 변경·연속 클릭에도 공급자 단위 동시성·간격 제한이 유지되는가?
- [ ] 대기열을 포함한 총 지연이 UI 제한 시간과 맞는가?
- [ ] 재시도 간격·Retry-After·최대 횟수가 호출 빈도와 무관하게 서버에서 강제되는가?
- [ ] 중복 요청은 기존 작업의 상태·타이머를 보존하며 거절하거나 같은 결과를 구독하는가?

## 설정 저장
- [ ] 외부에서 지운 개별 키가 다음 저장에서 되살아나지 않는가? — 사례: 디스크에 있는 키만 순회해 지운 토큰이 메모리에서 재기록.
- [ ] 섹션 삭제와 일부 필드 변경이 겹쳐도 다른 비밀값을 복원하지 않는가?
- [ ] 수정하지 않은 필드는 최신 상태를 쓰거나 저장 payload에서 빠지는가? — 사례: 오래된 초안 저장이 다른 화면의 최신 값을 덮음.
- [ ] 검증한 자격 증명과 실제 호출이 쓰는 자격 증명의 우선순위가 같은가?
- [ ] 저장 실패가 호출자에게 전달되고, 그 세대의 부분 상태만 정리되는가?

## 테스트
- [ ] 실제 생산자 → 전송 → 소비자 계약을 연결한 테스트가 있는가?
- [ ] 인증·출처 가드를 모의 허용 함수로 바꾸지 않고 실제 검증 함수의 거부 사례를 검사하는가?
- [ ] fixture만 비교하지 않고 현재 핸들러를 실제로 실행해 검사하는가?
- [ ] 기존 부작용 금지 검증(파일·프로세스·승인)을 유지하는가?
- [ ] 잘못된 기존 동작을 기대값으로 고정하지 않는가?
- [ ] 취소·재연결·재시작·느린 종료·저장 실패를 검증하고, 정적 확인과 실기 미검증을 구분해 적었는가?
