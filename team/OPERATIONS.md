# 운영 회고 — 무엇이 문제였고 무엇을 바꿨나

근거: 하루 반 동안의 실제 운영 기록(보고서 80여 개, 그중 교차 리뷰 40개, 릴리스 2회).

## 잘 된 것
- 교차 리뷰가 실제 보안 결함(P0)을 여러 번 잡았다(자격 증명 출처 검사 누락, 승인 위조, 승인 우회 등).
- 작은 브랜치 + 통합 브랜치 + 전체 테스트 → 릴리스 흐름이 안정적.
- 직원을 Codex로 돌려 Claude 사용량을 줄이면서 병렬 작업 수가 늘었다.

## 문제와 원인
| # | 문제 | 실제 사례 | 원인 |
|---|---|---|---|
| 1 | 리뷰 왕복이 너무 많다 | 한 기능 묶음에 리뷰 6회 | 체크리스트 없이 제출, 리뷰어가 diff만 보고 매번 새 각도에서 지적, 브랜치별로 따로 리뷰 |
| 2 | Codex 실행 실수 | 입력 대기로 1시간 멈춤, 읽기 전용이라 파일 못 읽음, 지시서 누락 | 매번 명령을 손으로 조립 |
| 3 | 현황을 놓침 | 완료 보고를 10시간 놓침 | "프로세스가 살아 있나"로 판단, 현황판 없음 |
| 4 | 같은 폴더 동시 작업 | 두 직원이 같은 worktree에서 타입 검사 흔들림 | 배정 규칙 부재 |
| 5 | 결정 번복 | 같은 제품 결정이 두 번 뒤집힘 | 사용자 결정 기록이 흩어져 있음 |
| 6 | 릴리스 수작업 | 압축·매니페스트·태그를 매번 손으로 | 릴리스 스크립트가 일부만 자동화 |
| 7 | 보고가 길고 알림이 잦다 | 중간 알림마다 사용자에게 답함 | 보고 형식·묶음 규칙 없음 |
| 8 | 지시서 밖 기능 | 요청 안 한 옵션·화면이 추가됨 | 범위 규칙 없음 |

## 바꾼 것
1. **Codex 실행기 `team/bin/run-codex.sh`** — 규칙·ADR·보고 형식 머리말 자동, `</dev/null`, 빈 지시서 거부, 보고서를 `team/reports/`에 저장. (2)
2. **현황판 `team/STATUS.md`** — 실행기가 시작·끝을 한 줄씩 기록. 진행 여부는 보고서 파일 유무로 판단. (3)
3. **보안 셀프 체크리스트** — 리뷰어가 잡은 패턴을 목록으로. 제출 전 항목별 확인 표를 보고에 첨부. (1)
4. **묶음 리뷰** — 같은 기능의 여러 브랜치는 합친 뒤 한 번에. 리뷰어는 처음부터 주변 코드 읽기 허용. (1)
5. **한 worktree = 한 사람.** (4)
6. **ADR** — 사용자 결정은 바로 ADR로. 확정 ADR은 다시 논의하지 않음. (5)
7. **릴리스 스크립트 한 명령화.** (6)
8. **보고 30줄 고정 + PL은 완료·결정 필요 시점에만 사용자 보고.** (7)
9. **범위 엄수 규칙** — 지시서 밖 변경 금지, 보고에 "지시서 밖 변경" 필수, PL이 머지 전 대조. (8)
